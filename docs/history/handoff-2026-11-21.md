## How to do the usual things

- **Checks:** `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm --filter ./apps/web test`,
  `pnpm --filter ./apps/backend test` (all passing at 1adbad7: web 120, backend 19). The Android build
  (`powershell -File scripts/Beacon-Android.ps1 -Action Build`) runs the Android unit tests and needs the change
  committed under `apps/android-host`; it takes 6-10 minutes, so run it in the background. Install with
  `adb install -r dist/BeaconRemoteHost-<commit8>.apk` (keeps the pairing; grant `RECORD_AUDIO` again and run
  `scripts/acceptance/Setup-Pixel.ps1 -Action Prepare` if accessibility or the battery exemption were reset).
- **Web-only production release** (what was done four times today): `git archive` the commit to
  `/opt/beacon-remote/releases/<full-sha>` on the VM, copy `compose.release-images.json` from the current release with
  the sha replaced, tag the unchanged backend and backup images with the new sha, `build web`, `up -d --no-deps web`
  through a wrapper like `beacon-remote-compose` pinned to the new release, check `/health` and the served asset hash,
  then repoint `/opt/beacon-remote/current` and `DEPLOYED_RELEASE`. Take the encrypted backup first
  (`sudo systemctl start beacon-remote-backup.service`) and tag the previous web image `rollback-<short>`. A release
  that changes the backend also needs `migrate` and `verify` with the old backend stopped (see
  [deployment.md](../deployment.md)). Never `compose down`, delete volumes or prune images.
- **Test-stack redeploy:** same idea with the `acceptance-images-*.override.yaml` chain listed in
  `docker inspect beacon-remote-acceptance-web` (compose config files label); add a new override as the last file.
- **Private test tooling** (outside the repo, `D:/Beacon-Secrets/remote/acceptance/preparation/<run>/`):
  `pixel-connect-2026-11-18.mjs` and its copy `emulator-connect.mjs` (driven by a command file piped to node's stdin,
  e.g. `tail -n 0 -f cmds | node script`; commands include `front`, `state`, `lat`, `viewshot`, `click <text>`,
  `js <expression>`, `size WxH`, `light`/`dark`), `windows-control.mjs`, `windows-control2.mjs` (clicks from the viewer),
  `windows-shot.mjs`, `windows-click.mjs`. They serve the **local** `apps/web/dist` for the Pixel/emulator scripts but
  the deployed test site for the Windows ones. Rebuild the web before running the local-dist scripts, and wait a few
  seconds after a build.
- **Pitfalls met:** the acceptance backend self-expires; the TURN relay refuses new sessions (error 486) after many
  quick sessions, wait about ten minutes; `adb` cannot set the clipboard; typing digits into a lock screen on the
  owner's phone is refused by policy (throwaway credentials on the dedicated test phone or emulator are fine);
  Surfiena sleeps; running two harness sessions at once ends the first.
